# Portfolio valuation boundaries

Portfolio cash belongs to the selected typed account. PLAYER and TEAM accounts remain separate even when their UUIDs match.

Goods belong to their typed storage owner. Portfolio holdings aggregate the existing storage-provider API's `portfolioHoldings(level, owner)` summaries. The built-in Vault/Tank adapter reports registered owned Vault item stacks and Tank fluids using exact commodity variant IDs and trade units (items or mB). Addon providers can opt in through the same default method; existing providers remain compatible and default to an empty summary. Providers must enumerate disjoint owned stores, exclude reserved units, avoid side effects and return only positive quantities. Ordinary inventory, ender chests and ordinary chests are not implicitly owned Economy storage. Built-in valuation checks whether the store's chunk is already loaded before every block-entity read. It never loads a chunk to produce a portfolio. Each physical store has a durable last-known quantity mark: unloaded stores retain that mark and are explicitly stale; stores never observed loaded are explicitly unknown and excluded from totals. Unknown is not asserted to mean empty. Loaded verification of a destroyed/missing store removes its old mark and indexes, so demolished stores do not accumulate permanent lookup work. A mark's physical key survives unload unregisters and moves to the new typed owner on team storage succession, preventing loss or duplication of unloaded assets.

Sell escrow, including expired/cancel-pending and quarantined recovery orders, remains owned until actually returned or delivered. It is included from active order state and durable recovery snapshots, deduplicated by order ID and provider/token. Live state wins over a stale saved copy. Provider escrow remains countable when its provider is missing. Built-in escrow uses actual retained item/fluid quantities, not requested order quantity. Virtual infinite/server supply is excluded. An order's typed `storageAccount` owns its escrow: when legacy team cash purchases use a member's personal stores, reserving/cancelling those goods must conserve personal holdings rather than moving their value into the team portfolio.

Unpaid compensation recorded by the existing recovery machinery is a receivable for its typed creditor and an equal liability for its typed debtor. Recovery state requiring manual intervention is a claim, not available spendable cash. Malformed raw NBT orders that cannot produce a validated order snapshot are preserved by existing quarantine storage but cannot be valued safely; no asset quantity is invented from opaque data.

Holdings are marked using the most recent valid trade price retained in Economy's existing bounded trade ledger, matched by exact commodity ID. An untraded commodity has a zero known mark; an order's arbitrary ask price is never a valuation source. Because the existing trade ledger retains its latest 1,000 trades, a commodity whose last mark ages out becomes unpriced. This is a known valuation-data boundary, not a realized gain/loss. Addon providers should report this same identity and unit convention.

Shared `PortfolioValuation` is used across Minecraft 1.20.1, 1.21.1 and 26.1.2. A valuation pass indexes the bounded trade ledger once, then multiplies each holding by its latest mark. There is no per-tick global account scan. Each selected owner's complete valuation (provider summaries, order/escrow snapshot, latest-price marks and owned/unreserved totals) is cached for at most one second, so bursts of generic credits and UI requests reuse it. Built-in registered-store enumeration has its own one-second cache and per-owner index: it never scans other owners' cache records. A loaded Vault/Tank mutation refreshes only that physical store and updates its owner's aggregate by a delta; market reserve/fill/edit/cancel invalidates the owner's valuation result without forcing another built-in full storage scan. Ownership/topology changes invalidate the affected record enumeration. External providers are re-read after market invalidation and are responsible for making their summary method side-effect-free and load-safe. Price-only and externally bypassed storage mutations become visible on the next one-second refresh; normal built-in mutations invalidate immediately.

The visible status reports counts of fresh, stale and unknown built-in stores. Fresh means verified loaded at the latest cache observation, which may be up to one second old. Stale quantities can remain older indefinitely while the chunk stays unloaded, including across server restarts; the UI retains their last known value explicitly rather than pretending they are current or zero. A previously unobserved unloaded store cannot have a safe invented quantity. Marks persist as a versioned NBT byte array, avoiding the NBT string size limit. An individual cold refresh still enumerates the selected owner's registered stores and order state; unusually large storage/order sets can make that refresh expensive. Assets are not arbitrarily truncated. Addon providers that do not implement a quantity summary remain an explicit API opt-in boundary; the built-in freshness status does not certify their data.

Legacy saves can have an aggregate portfolio asset mark without any per-store cache. If an unknown unloaded store exists and a previous history asset total exists, valuation preserves that previous total as explicitly stale instead of drawing a fabricated loss to zero. Until every store has been observed, that fallback cannot safely attribute later commodity valuation changes or reconstruct per-store quantities; known holding rows may therefore not sum to the retained stale total. Without a prior total, the result is conspicuously marked incomplete and includes known holdings only. Loading and observing the previously unknown stores removes the fallback.
